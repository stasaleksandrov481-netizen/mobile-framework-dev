# CORTEX — повторная проверка безопасности и восстановления БД (18.11.2026)

## Проверенные факты (после внешнего аудита)

- Supabase проект `jjcqrjztxohnifmziksy`, регион `eu-west-1` (Ирландия), Edge Function `cortex` ACTIVE **v48**, `verify_jwt=false`. Все **11 файлов** активной функции побайтно совпадали с `main` SHA `af48b0edfa71e31cacfe5c1ac1b1b2d3697c4f05` на дату проверки. Отсутствие gateway JWT-проверки означает, что функция сама обязана правильно проверять права и лимиты на каждом чувствительном маршруте; нельзя автоматически включать `verify_jwt=true`, поскольку предусмотрены гостевые/status-маршруты.
- `public.cortex_ai_device_identity` существует в production, её вызов закрыт для `anon` и `authenticated`, а определение на случай восстановления уже лежит в `supabase/migrations/20261117080100_cortex_device_identity_baseline.sql`. Отсутствие **именно этой** функции в Git больше не подтверждается.
- Существенная подтверждённая проблема: **15 версий из `supabase_migrations.schema_migrations` отсутствовали в Git**. Этот PR восстанавливает их из сохранённых в БД массивов `statements`, сохраняя оригинальные версии и SQL. Два ранее неверно датированных файла с идентичным содержимым заменены именами production-версий. Локальная, отличающаяся от фактически исполненной миграция `20261116210500_expand_free_ai_daily_budget.sql` перемещена в `archived-migrations`, чтобы повторное развёртывание не выполняло её как исторически применённую.
- После восстановления версий **ещё требуется** пустая тестовая БД и полный прогон миграций с фиксацией diff. `20261117080100_cortex_device_identity_baseline.sql` — локальный восстановительный baseline, отсутствует в журнале production, поэтому нужно проверять совместимость с 15 восстановленными миграциями. Этот PR **не меняет действующую БД**, не гарантирует её безусловную воспроизводимость и не вносит данных пользователей в Git.
- Активный Vercel WAF v10 блокирует типовые сканирующие пути и ограничивает `/api/status` (120/мин/IP), но `gen`, `rce`, `sqli`, `xss` и bot protection находятся в `log`. На домене наблюдалась DDoS-аномалия 18.11.2026 18:45 UTC с платформенным challenge. Прямой `*.supabase.co` путь **не проходит через Vercel WAF**.
- `X-Cortex-Device` подделываем: проверка подписи APK на клиенте не заменяет серверную аппаратную аттестацию. Ограничения по аккаунту, глобальный атомарный предел AI и бюджеты нельзя снимать. Глобальный лимит из `main` синхронизирован с Edge v48.
- Security Advisor показывает `auth_leaked_password_protection`, а также предупреждения по SECURITY DEFINER. Процедуры администрирования, проверенные выборочно, требуют учётную запись, роль и MFA; предупреждение о доступности RPC само по себе не доказывает обход. Не отзывать массово `EXECUTE` без анализа вызывающих клиентов; публичная функция цен `cortex_stars_public_prices` ожидаемо возвращает прайс.
- Фактические тарифы в БД: `guest=15000`, `free=30000` модельных токенов/сутки. Это **не** значения из внешнего отчёта (5000), и эти значения не равны гарантированным бесплатным запросам OpenRouter. `funded_micros=8000000` — поле внутренней конфигурации, а не подтверждённый баланс OpenRouter.

## Открытые риски / действия владельца

1. **Локализация ПД РФ и трансграничная передача:** проверить применимость 152-ФЗ с юристом по фактическому потоку данных. Supabase в Ирландии: документы/галочка на сайте **не заменяют** требуемую локализацию при сборе ПД граждан РФ. Продумать перенос хранения/первичного сбора, оформление уведомлений и поручений обработки. Без решения — не открывать свободную публичную регистрацию граждан РФ.
2. **Supabase Auth:** включить leaked-password protection на поддерживающем тарифе (по текущим документам Supabase Pro+), оценить CAPTCHA и MFA. CAPTCHA включать только одновременно с передачей `captchaToken` со всех клиентов, иначе вход/регистрация сломаются.
3. **Аппаратная аттестация:** выбрать протокол для sideload/RuStore и устройств без GMS, реализовать серверные nonce, проверку сертификатов/связанного ключа и anti-replay; `PLAY_RECOGNIZED` не считать обязательным для всех sideload APK.
4. **Подпись APK:** сверить SHA-256 сертификатов старой 1.0.11 и новой 1.0.18-beta.1 через `apksigner verify --print-certs` на двух **реальных APK**. Если подписи различаются — обновление поверх не сработает: предусмотреть экспорт/импорт локальных чатов и сценариев и предупредить тестеров; старый ключ может быть единственным способом бесшовного обновления.
5. **Финансовая защита:** фактический остаток, баланс и лимиты OpenRouter сверять в аккаунте поставщика; внутреннее поле `funded_micros` это не подтверждает. Проверить отказ (429) глобального лимита без реального списания. Контроль нагрузки на Edge и расходы Vercel выполнять отдельно.
6. **Тестовый прогон миграций:** восстановить пустую тестовую БД; сравнить функции, политики, GRANT, ограничения и схему с production. Только после теста обсуждать применение локального baseline к production. Прямой SQL из Git в production этим PR не выполнялся.
7. **Публичный релиз:** проверить реальные телефоны с банковскими приложениями/без, permissions, безопасную обработку чувствительных экранов и согласия. Доступ Accessibility не доказывает удалённый захват, но повышает последствия возможной уязвимости.

## Граница изменений

Этот PR меняет только историю SQL/документацию. Не меняет Edge, Vercel Firewall, Android APK, облачные настройки, таблицы и данные пользователей. История SQL восстанавливается из `supabase_migrations.schema_migrations.statements[1]`, никаких SQL-команд в production не исполняется.
