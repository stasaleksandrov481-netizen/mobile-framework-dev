# Три критичных усиления безопасности CORTEX — 17.11.2026

Данный пакет не изменяет Android UI и не включает принудительное отключение старых APK.

## 1. Контроль подписи Android APK (частичная защита)

- `app/build.gradle.kts` вычисляет SHA-256 сертификата из выбранного release keystore и внедряет его в `BuildConfig`. Сам keystore и пароли в код не попадают.
- `CortexApkIntegrity.kt` сравнивает действующую подпись установленного APK с build-time сертификатом в release; debug-сборки сохраняют текущий режим.
- `CortexServerBridge.kt` не отправляет `X-Cortex-Device`, если у release-пакета подпись не совпадает.
- Это обнаруживает случайную подмену/переподписание APK, но **не является полноценной аттестацией устройства**: атакующий, модифицировавший приложение, способен удалить локальную проверку. `X-Cortex-Device` остаётся подделываемым заголовком.

**Для подтверждения подлинности устройством и сервером** нужен отдельный проверяемый протокол: серверный одноразовый nonce, Android Keystore attested ECDSA key, отправка цепочки сертификатов, проверка корня доверия Google/доверенного OEM и статуса отзыва, `attestationChallenge`, аппаратного security level, verified boot, package name и SHA-256 подписанта в attestationApplicationId, затем подпись запроса с защитой от повторов. Включать fail-closed только для подписанной и одобренной версии с поддержкой устройств без Google-сервисов. Для RuStore/sideload **нельзя** по умолчанию требовать `PLAY_RECOGNIZED`.

## 2. Реальная защита прямого Supabase API от подмены IP

- До исправления `peer()` выбирал `cf-connecting-ip` или **первый X-Forwarded-For**, который можно подставить со стороны клиента. Это позволяло менять ключи IP-rate limit.
- После исправления используются только валидные `CF-Connecting-IP` от hosted Supabase ingress; при отсутствии такого значения используется **один общий unknown bucket**, а не пользовательский XFF.
- Raw IP не сохраняется; ключ хэшируется с новой версией префикса, старые временные IP-бакеты не переиспользуются. Глобальный лимит гостей, лимит устройства/аккаунта и атомарная запись остаются.
- Регрессионный тест проверяет, что подстановка двух разных XFF не меняет бакет, а два доверенных IP создают разные.

**WAF Vercel отдельно**: существующие `gen/rce/sqli/xss` по-прежнему `log`. Прямой адрес `*.supabase.co/functions/v1/cortex` обходит Vercel WAF, поэтому IP-бюджеты должны оставаться внутри Edge. Нельзя обещать, что включение Vercel WAF перекроет прямые вызовы. Переключать managed CRS в блокировку можно только после анализа трафика, теста в preview и ручного `publish` владельцем; не переводить Android API на браузерный challenge.

## 3. Воспроизводимая приватная SQL-модель

- Новая `supabase/migrations/20261117080100_cortex_device_identity_baseline.sql` воспроизводит структуру из действующей БД:
  - `cortex_private.ai_device_owners`, `ai_guest_owners`;
  - RLS для обеих таблиц и только service-role grants;
  - `public.cortex_ai_device_identity(text,text,text)` с тем же атомарным `advisory_xact_lock(140387,1)` и сохранением истории квот;
  - `EXECUTE` закрыт для `PUBLIC`, `anon`, `authenticated`, доступен `service_role`.
- Миграция повторно применима к текущему состоянию; существующие строки не удаляет. Перед применением на production сравнить functiondef, grants, ограничения, затем протестировать на копии БД.
- В релизе нельзя использовать `SECURITY DEFINER` как обход RLS.

## Релизные границы

- Android: **не выпускать подписанную APK** до определения правильной UI-ветки и проверки на реальном устройстве.
- Supabase Edge: серверный код меняется только после успешных Edge-тестов и сверки с живой v44; источник истины — действующий production snapshot.
- Vercel Firewall: новые блокирующие правила без замера реального трафика не публиковать.
- В этой ветке исходники защищены, но production не считается обновлённым до подтверждения реальной версии Edge/DB/APK.
