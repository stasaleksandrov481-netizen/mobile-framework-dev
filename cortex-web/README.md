# CORTEX. Сайт приложения

Стек: Next.js 16 (App Router), React 19, TypeScript. Шрифт Onest Variable хранится локально. Сайт оформлен в чёрно-белом стиле Android-приложения.

## Запуск

```bash
npm ci
npm run dev
npm run build
npm start
```

Сайт открывается на http://localhost:3000. Для Vercel корневая директория проекта: `cortex-web`.

## Что готово

- На лендинге больше нет недостоверной 3D-модели телефона.
- Отдельная страница `/register` с формой слева и лёгкой сеткой на canvas справа. На экранах до 900 px декоративная панель полностью скрыта.
- Сетка работает без WebGL и не перерисовывается непрерывно в состоянии покоя; в центре вместо круга — типографика.
- Локальный Onest Variable без Google Fonts.
- Одноэкранный адаптивный лендинг без декоративных разделителей и второстепенных секций.
- Форма регистрации и подтверждения email использует тот же Supabase Auth-проект, что и Android. Вход по шестизначному коду подготовлен, но скрыт до подключения и проверки SMTP.
- Предрегистрации сохраняются в таблицу `cortex_preregistrations` с RLS; бонус 5 000 токенов **резервируется** до беты, он не расходуется и не начисляется в AI-бюджет до подключения серверного механизма выдачи.
- Ссылка на установку скрыта до 20.11.2026 и появляется только при заданном `NEXT_PUBLIC_CORTEX_ANDROID_DOWNLOAD_URL`.
- SEO title/description/OpenGraph, favicon, базовые HTTP-заголовки безопасности.
- В `app/layout.tsx` добавлен `mailru-domain` для подтверждения VK Workspace.
- Разделы `/privacy`, `/terms`, `/permissions` и `/support` описывают обработку данных, условия приложения и подписок, разрешения Android и способы связи. `/pricing` получает текущие цены и квоты из каталога Supabase.
- Совместные операторы ПДн и исполнитель платных услуг задаются закрытыми переменными `CORTEX_LEGAL_OPERATOR_A_*` и `CORTEX_LEGAL_OPERATOR_B_*`. Второй оператор одновременно является единственным исполнителем платных услуг. ФИО и ИНН нельзя сохранять в публичном GitHub: укажите их в конфигурации продакшен-сервиса. До заполнения адресов и устранения вопроса локализации регистрация должна оставаться закрытой. Сведения перед запуском перечислены в `legal/`.
- Серверный модуль для отдельной Upstash Redis (`lib/redis.ts`) и `GET /api/status`, который проверяет доступность Redis без раскрытия ключей.
- Честное позиционирование: публичная бета запланирована на **20.11.2026**, скачивание APK пока не включено.

## Upstash Redis

Создайте **отдельную** Redis-базу для CORTEX. Не используйте `smetraProduction`.

1. Добавьте в окружение Vercel значения `UPSTASH_REDIS_REST_URL` и `UPSTASH_REDIS_REST_TOKEN` из Upstash. Эти переменные серверные, префикс `NEXT_PUBLIC_` запрещён.
2. Локально используйте `.env.local` по образцу `.env.example` (файл исключён из Git).
3. Проверьте `/api/status`: ответ `{"status":"ok"}` означает, что сервер соединился с Redis. Ответ 503 означает, что конфигурация недоступна или соединение не удалось.

Сайт может открываться без Redis. Эта интеграция готовит серверное соединение, но пока не хранит пользовательские данные.

## Предрегистрация

### Готовность к большому наплыву

- Главная и форма регистрации полностью статические; на главной не загружается SDK Supabase Auth. Юридические страницы тоже собираются в статический HTML. Обновление `CORTEX_LEGAL_*` требует повторной сборки и деплоя.
- Регистрация дополнительно закрыта на уровне UI, пока не выставлены `CORTEX_ENABLE_REGISTRATION=true`, `CORTEX_RF_DATA_COMPLIANCE_VERIFIED=true` и полные реквизиты обоих операторов в `CORTEX_LEGAL_OPERATOR_A_*`/`CORTEX_LEGAL_OPERATOR_B_*`. Эти флаги включаются только после выполнения юридических и технических требований. Прямые запросы к Supabase Auth нужно защищать отдельно настройками Auth — UI-флаг их не блокирует.
- По отдельному указанию владельца доступно временное исключение для публичной беты: **одновременно** `CORTEX_ENABLE_REGISTRATION=true` и `CORTEX_PUBLIC_SIGNUP_EXCEPTION=true`. Оно не требует и не подделывает `CORTEX_RF_DATA_COMPLIANCE_VERIFIED`, не меняет Supabase Auth и не означает юридического соответствия. Откат: установить `CORTEX_PUBLIC_SIGNUP_EXCEPTION=false`, собрать и задеплоить сайт заново. Риски и незакрытые требования зафиксированы в `security/RELEASE-GATE.md`.
- `/pricing` использует ISR на 300 секунд вместо запроса Supabase на каждое открытие. Сверяйте актуальные цены с серверным каталогом в момент оплаты.
- **Не открывайте регистрацию, пока не проверена исходящая почта и лимиты Auth.** В Supabase Dashboard: Authentication → SMTP Settings и Authentication → Rate Limits. Для custom SMTP первоначально действует низкий проектный лимит email (документация Supabase описывает 30/час); изменение лимита в Supabase не увеличивает пропускную способность VK Workspace.
- Чтобы выдерживать тысячи регистраций за час, сначала согласуйте лимит и репутацию отправителя с транзакционным email-провайдером; затем установите в Supabase проектную квоту чуть ниже подтверждённой пропускной способности. Не выставляйте «безлимит» или произвольные тысячи/час без согласованного SMTP.
- Перед запуском включите CAPTCHA в Supabase Auth на signup, OTP и recovery. Выбранный виджет должен передавать `captchaToken` при каждой защищённой операции; включение капчи только на стороне Supabase без изменения формы сломает регистрацию.
- Публичные страницы можно тестировать локально `node qa/load-cortex.mjs http://127.0.0.1:3100` после запуска production-сервера на этом порту. Сценарий не создаёт аккаунты и не отправляет почту. Тест локального процесса не гарантирует квоты Vercel, SMTP или Supabase в продакшене.
- Не снимайте защиту Vercel Authentication для всего проекта до проверки согласий, локализации данных, SMTP и оператора персональных данных.

1. SQL-миграция `supabase/migrations/20261115171814_cortex_preregistration.sql` **применена к проекту CORTEX** (`jjcqrjztxohnifmziksy`). Миграция создаёт таблицу, ограничивает доступ с помощью RLS и запрещает клиенту менять бонусные начисления.
2. В Supabase Auth разрешить email/password signup, включить подтверждение почты и добавить `https://cortexapp.ru/auth/callback` в список разрешённых Redirect URLs. Email-шаблон должен содержать ссылку подтверждения либо код OTP.
3. При необходимости переопределить публичные значения `NEXT_PUBLIC_CORTEX_SUPABASE_URL` и `NEXT_PUBLIC_CORTEX_SUPABASE_PUBLISHABLE_KEY` (в коде уже заданы те же публичные значения, что используются в `cortex-control`).
4. Перед стартом беты настроить почтового провайдера и **серверную** отправку уведомлений по `notify_opt_in`, не передавая email-список браузеру. Само наличие флага согласия ещё не отправляет письмо. Подготовленный обработчик и миграция описаны ниже; они не активируются сами собой.
5. Перед начислением бонуса реализовать в серверном `cortex_ai_reserve` однократное списание бонусных кредитов по подтверждённым аккаунтам. Колонка `bonus_tokens` — резерв, изменять её из браузера нельзя.
6. Для автоматического входа после установки Android-разработчику нужна обработка App Link с **одноразовым серверным кодом**, привязанным к Supabase Auth ID. Постоянный bearer-токен нельзя помещать в URL. Пока Android не поддерживает обмен кодом, пользователь сможет войти с той же почтой и паролем.

В Vercel задать `NEXT_PUBLIC_CORTEX_ANDROID_DOWNLOAD_URL` только после готовности подписанного APK или страницы релиза. Кнопка не открывает пустой адрес.

## VK Workspace: noreply@cortexapp.ru и вход по коду

Статус: **код готов, подключение внешнего SMTP ещё не подтверждено**. Не включайте `NEXT_PUBLIC_CORTEX_EMAIL_OTP_READY` без успешного теста реальной доставки.

1. В настройках ящика `noreply@cortexapp.ru` создайте отдельный **пароль для внешнего приложения**. Не публикуйте пароль и не отправляйте его в чат; вводите только в секреты Supabase/Vercel.
2. В Supabase Dashboard проекта `jjcqrjztxohnifmziksy` откройте Authentication → SMTP Settings и подключите Custom SMTP. Укажите отправителя `noreply@cortexapp.ru`, сервер `smtp.mail.ru`, SSL/TLS порт `465`, логин `noreply@cortexapp.ru` и пароль внешнего приложения. При необходимости проверьте допустимые настройки шифрования для своего тарифа VK Workspace.
3. В Authentication → Email Templates примените три фирменных HTML-шаблона: `email-templates/otp.html` для **Magic Link**, `email-templates/confirm-signup.html` для **Confirm signup**, `email-templates/recovery.html` для **Reset Password**. Укажите темы «CORTEX · Код для входа», «CORTEX · Подтверждение почты», «CORTEX · Восстановление доступа». В каждом письме используется штатная переменная Supabase `{{ .Token }}`: это шестизначный код, а не фиксированное значение. Перед включением регистрации проверьте реальные письма и подтверждение с тестового аккаунта.
4. С тестового **существующего** аккаунта проверьте отправку кода, его ввод, неверный код, повторную отправку и частотные ограничения в Supabase Auth. Вызов `signInWithOtp` использует `shouldCreateUser: false`: код входа не должен создавать учётную запись автоматически.
5. Только после успешного теста поставьте в Vercel `NEXT_PUBLIC_CORTEX_EMAIL_OTP_READY=true` и задеплойте сайт. Пока переменная отсутствует или `false`, ссылка на вход по коду скрыта, парольный вход остаётся доступным.

### Однократное уведомление о выпуске беты

Доставка не включится до фактического релиза и наличия всех серверных секретов. Подготовлены `app/api/internal/notify-beta/route.ts`, ежедневный Vercel Cron в `vercel.json` (09:00 UTC, 12:00 МСК) и **отдельный не применённый** SQL-скрипт `sql/launch_notification_queue.sql`.

1. После проверки в Supabase SQL Editor проекта CORTEX примените `sql/launch_notification_queue.sql` и убедитесь, что RPC `cortex_claim_beta_notifications` доступна **только service_role**. Не применять к другой базе или без ревью.
2. Только в настройках **production** Vercel-проекта `cortex` установите серверные `CORTEX_SUPABASE_URL`, `CORTEX_SUPABASE_SERVICE_ROLE_KEY`, `CORTEX_SMTP_USER`, `CORTEX_SMTP_APP_PASSWORD`, `CRON_SECRET`. Пример имён переменных есть в `.env.example`; никаких реальных ключей в Git нет.
3. Пока APK не опубликован, оставьте `CORTEX_BETA_RELEASED=false`. После выпуска укажите проверенную HTTPS-ссылку в `CORTEX_BETA_DOWNLOAD_URL`, установите `CORTEX_BETA_RELEASED=true` и выполните контролируемую тестовую отправку. Даже при `true` сообщения не начнут отправляться ранее **20.11.2026 00:00 МСК**.
4. Получателей выбирает сервер только по `notify_opt_in=true` и `notified_at IS NULL`. Каждая запись атомарно резервируется, чтобы параллельные запуски не отправляли дубликаты. Успешную передачу SMTP записываем в `notified_at`; при ошибке отправки резерв освобождается. При сбое после приёма письма SMTP, но до записи статуса, возможен повтор, поэтому перед массовой рассылкой нужно протестировать этот сценарий и предусмотреть ручное устранение дубликатов.
5. Vercel вызывает Cron ежедневно. Для отправки точно в момент открытия релиза администратор может отдельно вызвать защищённый маршрут с `Authorization: Bearer <CRON_SECRET>` через согласованный серверный механизм; не помещать `CRON_SECRET` в URL, браузерный JS или сторонний лог.

Отправление касается только одного письма **о запуске** для добровольно согласившихся и подтвердивших адрес. Оно не даёт разрешения на маркетинговые письма. Для масштабной рассылки проверьте лимиты VK Workspace и репутацию домена (SPF/DKIM/DMARC).

## Домен cortexapp.ru

Домен уже подключён к Vercel, а авторитетная DNS-зона `cortexapp.ru` активна в Cloudflare. Изменения записей делаются в Cloudflare; REG.RU остаётся регистратором.

**Не удалять и не перезаписывать MX, TXT, DKIM, SPF, DMARC записи VK Workspace.** Смена NS целиком не требуется. После распространения DNS проверьте HTTPS и страницу, затем нажмите «Проверить» в VK Workspace для метатега.

## Ограничения

Регистрация зависит от применённой SQL-миграции и настроенного Supabase Auth. Автовход в Android, полноценная настройка отправки писем и фактическое начисление бонусов требуют отдельного серверного этапа и интеграции в приложение. До коммерческого запуска необходимо определить, кто из совладельцев выступает оператором данных и стороной договора, заполнить реквизиты, проверить размещение базы и согласия — см. `legal/LAUNCH-CHECKLIST.md`.
